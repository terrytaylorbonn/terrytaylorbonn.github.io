# Demo: Rule-Based Anomaly Detection

## Goal

```text
raw_events → score events → flagged_anomalies
```

No AI. No model. No ontology yet.

---

## 1. Create a new Pipeline Builder pipeline

Name:

```text
sterile_anomaly_demo
```

Start with:

```text
Manually enter data
```

---

## 2. Create input table: `raw_events`

Columns:

| column | type |
|---|---|
| `event_id` | string |
| `entity_id` | string |
| `value` | double |
| `status` | string |
| `expected_status` | string |

Rows:

| event_id | entity_id | value | status | expected_status |
|---|---|---:|---|---|
| E001 | A | 25 | OK | OK |
| E002 | A | 140 | OK | OK |
| E003 | B | 40 | ERROR | OK |
| E004 | B | 75 | OK | OK |
| E005 | C | 200 | ERROR | OK |
| E006 | C | 10 | OK | OK |
| E007 | D | 95 | WARN | OK |
| E008 | D | 15 | OK | OK |

---

## 3. Add a transform: create anomaly reason

Add a calculated column:

```text
anomaly_reason
```

Logic:

```text
if value > 100 → HIGH_VALUE
else if status != expected_status → STATE_MISMATCH
else NORMAL
```

If Pipeline Builder has a formula/CASE expression, use:

```sql
CASE
  WHEN value > 100 THEN 'HIGH_VALUE'
  WHEN status != expected_status THEN 'STATE_MISMATCH'
  ELSE 'NORMAL'
END
```

Name this intermediate dataset/node:

```text
scored_events
```

---

## 4. Filter anomalies

Add a **Filter rows** transform:

```text
anomaly_reason != NORMAL
```

Output node:

```text
flagged_anomalies
```

Expected flagged rows:

| event_id | reason |
|---|---|
| E002 | HIGH_VALUE |
| E003 | STATE_MISMATCH |
| E005 | HIGH_VALUE |
| E007 | STATE_MISMATCH |

Expected count:

```text
4 anomalies out of 8 events
```

---

## 5. Add output datasets

Create two outputs:

```text
scored_events
flagged_anomalies
```

If you only want one output, use:

```text
flagged_anomalies
```

---

## Final pipeline diagram

```mermaid
flowchart LR
    A["raw_events<br/>8 sterile test rows"] --> B["scored_events<br/>add anomaly_reason"]

    B --> C["flagged_anomalies<br/>filter anomaly_reason != NORMAL"]
```

## What this proves

This demo proves the classic non-AI Palantir pattern:

```text
ingest data → apply rules → identify anomalies → create operational output
```

# Workshop setup: Filter Anomaly Events by Anomaly Reason

## Goal

Create a Workshop app where:

```text
Right widget = filter by Anomaly Reason
Left widget = object table showing matching Anomaly Events
```

Expected behavior:

- Before selecting a filter, the table shows all anomaly events.
- If user selects `HIGH_VALUE`, the table shows only `HIGH_VALUE` rows.
- If user selects `STATE_MISMATCH`, the table shows only `STATE_MISMATCH` rows.
- The filter widget itself must still show both choices.

---

# 1. Add Ontology object type

In Workshop, add the Ontology object type:

```text
Anomaly Event
```

This is the object type created from the `flagged_anomalies` dataset.

Important properties:

```text
Event Id
Anomaly Reason
Entity Id
Value
Status
Expected Status
```

`Event Id` is also configured as the object title.

---

# 2. Create variable: `All Anomaly Events`

Create an **Object set** variable.

Name:

```text
All Anomaly Events
```

Definition:

```text
Object type = Anomaly Event
No filters
```

Purpose:

> This is the complete unfiltered set of anomaly objects.

This variable is used by the **filter widget**.

Do **not** apply the selected filter to this variable.

---

# 3. Create variable: `Selected Anomaly Reason Filter`

Create an **Object set filter** variable.

Name:

```text
Selected Anomaly Reason Filter
```

or if Workshop auto-renames it:

```text
Selected Anomaly Reason Filter1
```

Default value:

```text
No filters
```

Purpose:

> This variable stores the filter condition selected by the user.

Important:

```text
This is not the filtered data.
This is only the selected filter criteria.
```

Example:

If user selects `HIGH_VALUE`, this variable represents:

```text
Anomaly Reason = HIGH_VALUE
```

---

# 4. Create variable: `Filtered Anomaly Events`

Create another **Object set** variable.

Name:

```text
Filtered Anomaly Events
```

Definition:

```text
Object type = Anomaly Event
```

Then add filter:

```text
Using a variable = Selected Anomaly Reason Filter
```

or, if the actual variable name has `1`:

```text
Using a variable = Selected Anomaly Reason Filter1
```

Purpose:

> This object set applies the selected filter criteria and produces the rows the table should show.



This produces filter options like:


## Output data

Set filter output to:

```text
Selected Anomaly Reason Filter
```

or:

```text
Selected Anomaly Reason Filter1
```

Purpose:

> The filter widget writes the user's selected criteria into this variable.

# 10. Main mistake to avoid

Do **not** connect the filter widget to:

```text
Filtered Anomaly Events
```

If you do that, the filter widget filters itself.

Bad wiring:

```text
Filtered Anomaly Events
        ↓
Filter List
        ↓
Selected filter
        ↓
Filtered Anomaly Events
```

That causes the problem you saw:

> selecting `HIGH_VALUE` makes `STATE_MISMATCH` disappear from the filter widget.

Correct wiring:
