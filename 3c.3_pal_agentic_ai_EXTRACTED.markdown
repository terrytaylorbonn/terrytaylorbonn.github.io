#### Q1: deleting the old marketplace is complicated

Yes—potentially, because the old Marketplace installation owns the foundation you are planning to reuse:

- Patient and Clinical Trial object types
- Ontology Actions
- datasets and pipeline
- Workshop UI

Your new Logic and Automation will reference those existing resources. Deleting/uninstalling the old Marketplace product could therefore break the new implementation.

For now, the safest arrangement is:

```text

Keep Marketplace installation
├─ reuse its data, Ontology and Actions
├─ pause old Automation
└─ create new Logic, Function, Evaluation and Automation

```

Only remove the Marketplace installation if you intend to remove the entire demo and have first checked all downstream dependencies. Deleting just the old Logic, Evaluation Suite, Function, or Automation is more manageable, but it is unnecessary if they are clearly named and disabled.

#### Q1: what i mean is, if i want to start clean, then getting rid of the existing stuff is not a simple delete.

Correct. A D3 installation is not one self-contained folder that can necessarily be removed with a single ordinary delete. It creates a **dependency graph across Foundry applications**:

```text
Automation
→ published Function
→ AIP Logic
→ Action
→ object types
→ datasets/pipeline
```

It may also include:

- an Evaluation Suite;
- Workshop resources;
- generated Ontology objects;
- user edits written through Actions.

Marketplace may provide an **uninstall/delete installation** operation for resources it manages, but:

- downstream resources you created manually may not be included;
- active references can block deletion;
- shared resources must not be removed;
- Ontology resources and generated data need special care.

A manual cleanup generally proceeds in reverse dependency order:

1. Pause/delete Automations.
2. Remove Evaluation Suites and application references.
3. Retire/remove published Functions and AIP Logic.
4. Remove Workshop dependencies.
5. Remove Actions.
6. Remove object/link types.
7. Remove pipelines and datasets.
8. Remove the Marketplace installation record.

Therefore, if the objective is simply to repeat the tutorial cleanly, **creating a second set of Logic/Evaluation/Function/Automation resources while retaining the Marketplace foundation is much safer**.

For complete isolation, a new namespace with its own Ontology is cleaner than trying to dismantle and recreate everything in the existing namespace. A new folder alone does not provide that isolation.

### P2 Add (4) AIP logic / (4a) Use LLM (Build the AIP Logic reasoning)

#### Q1: i saved this aip_logic and tested. but did not publish.

publish will create the function, and i will not be able to change that function?
(only can create new version)

**Correct.**

Publishing will:

1. Create the Function identity in the Function Registry.
2. Create its first immutable published version.
3. Leave the source AIP Logic editable.

Afterward:

```text
Edit AIP Logic
→ preview/test
→ publish again
→ create a new immutable Function version
```

**You cannot change the implementation of an already published version.**

**One important point: your current Logic outputs the **Use LLM struct**. If the intended final Function should output **Ontology edits**, add and configure the Action block before the first publication. Changing from a struct output to Ontology edits later is a breaking interface change.**

#### Q2: breaking interface change? what does that mean?

A **breaking interface change** means changing the Function’s public contract so existing callers can no longer use it in the same way.

Your current output is:

```text
Struct {
eligibility_decision: String
eligibility_reasoning: String
}
```

After adding the Action as the output, it becomes:

```text
List<Ontology Edits>
```

Those output types are incompatible. A caller expecting decision fields cannot consume a list of edits.

```text
Before:
Function → decision/reasoning struct
After:
Function → Ontology edits
```

Therefore, existing Automations, applications, evaluations, or other functions might need to be reconfigured. This generally requires a major version or a separate Function identity rather than an automatic compatible upgrade.

Because you have **not published yet**, there is no problem. If your intended final function should modify the Ontology, add the Action first and then publish.

Alternatively, intentionally keep two functions:

```text
Assess Eligibility
→ returns decision/reasoning
Review Patient
→ calls assessment
→ returns Ontology edits
```

That cleanly separates reasoning from writeback.

#### Q3: so its very important to create action and test BEFORE creating the function?

**Yes—if the final Function is supposed to modify the Ontology.**

Recommended order:

```text
Create AIP Logic
→ configure Use LLM
→ add and configure Action
→ preview proposed edits
→ evaluate
→ publish Function
```

This ensures the first published Function has the intended contract:

```text
Inputs: Patient + Clinical Trial
Output: Ontology edits
```

You can continue changing its internal prompts and reasoning afterward and publish new compatible versions, provided the inputs and output type remain compatible.

Publishing before adding the Action would create a different contract—a Function returning a decision struct rather than Ontology edits. That is appropriate only if you intentionally want a separate read-only assessment Function.

#### Q4: so evaluate is important before creating function?

but for my simple demo i want to leave evaluate out....
do it at the end.... to avoid too much complexity.

**No. Formal evaluation is not required before publishing.** It is a recommended quality-control step.

For your simplified demo, this order is reasonable:

```text
1. Build AIP Logic
2. Add the Action
3. Preview manually
4. Publish the Function
5. Create Automation
6. Add an Evaluation Suite later
```

The important requirement is to **preview and manually verify the complete Logic—including its Action and output type—before publishing**.

For production, evaluation should normally happen before enabling automatic edits. For a teaching demo, moving Evaluation to an optional final chapter reduces complexity and keeps the main architecture easier to understand.

### P3 Add (4) AIP / (4b) Action (Add Ontology modification)

#### Q1: So this is a successful test of aip_logic.
what is "Function inputs"... this really confused me, because there is no function yet.

**Yes, this is a successful preview test of the complete AIP Logic.** It generated the decision and proposed the expected Ontology edits, but did not apply them.

**“Function inputs” means the test values supplied to the AIP Logic’s declared inputs:**

- `patient` → Sita Menon
- `clinicalTrial` → Glycurex for Type 2 Diabetes

The terminology is confusing because Foundry treats an AIP Logic as an **unpublished function definition** while you are authoring it.

```text
AIP Logic before publication
= editable function definition
After publication
= registered, versioned Function
```

**Therefore, “Function inputs” does **not** mean that a published Function already exists. It means:**

> Inputs for this preview execution of the Logic that may later be published as a Function.

**A clearer UI label would have been **“Logic preview inputs.”****

### P4 Publish the (3) AIP Logic as a Function

#### Q2: all of these details.. and none of them explained in teh demo doc.

**Agreed. The demo provides the required clicks but does not explain the underlying lifecycle:**

```text
Create AIP Logic
→ define inputs
→ configure LLM
→ add Action
→ preview proposed edits
→ bind Logic to an Ontology
→ publish immutable Function version
→ select that Function in Automate
→ bind runtime inputs
→ choose approval or automatic execution
→ activate monitoring
```

Several distinctions are left implicit:

- An AIP Logic is treated as a function definition before publication.
- “Function inputs” in Preview are actually Logic preview inputs.
- Referencing Ontology objects is not the same as formally binding the Logic to that Ontology.
- Previewed edits are not committed.
- Publishing creates a versioned Function Registry entry.
- The published Function is an immutable snapshot, not a live reference to the editable draft.
- Automate invokes a selected published version.
- The Action block produces edits; Automate determines whether they are staged or committed.

These are not peripheral details—they determine how the system actually works. Your rewritten documentation is valuable because it explains the resource model and lifecycle rather than merely reproducing the screen sequence.

### 1. Resources in your new folder

**Yes.** You create:

- AIP Logic
- Evaluation Suite
- Automation

Publishing the AIP Logic automatically creates the Function entry; it is not another file you manually create in the folder.

### 2. Function and source AIP Logic

**Yes.** The Function is registered with the Ontology/Function Registry and has a fixed source AIP Logic.

Each published version is an immutable snapshot:

```text
One AIP Logic
├─ Function version 1.0.0
├─ Function version 1.0.1
└─ Function version 1.1.0
```

### 3. Creating a Function from scratch

**Yes.** To create a new, independent Function from scratch, create a new AIP Logic and publish it.

To create only a new version of an existing Function, modify its existing source AIP Logic and publish again.

### 4. Sort Functions by date

Click the **Published Date** column heading to sort ascending or descending.

That sorts by publication date, not necessarily the original creation date. The Functions list does not appear to expose a separate **Created Date** column. If you need clearer long-term organization, use consistent name prefixes, source names, and owning projects.

#### i click on that header.... there is no link... i think its an error

You are correct. **Published Date is not sortable in that table.** Only **Name** shows a sort indicator.

My previous instruction was wrong. This is either a UI limitation or defect in Ontology Manager.

Practical workarounds:

- use date/version prefixes in function names;
- search by function or source Logic name;
- use the **Owning project** and **Source** columns;
- inspect individual Function details for publication dates.

There is no visible way in that dialog to order the complete list by publication or creation date.
